# GPU-RHI profiling/benchmark harness (`gpu-bench`)

## Work done

Added a CPU-timed benchmark harness for the GPU RHI, built against the public API only (no
engine source touched). It rides the existing `mel_add_test` scaffold so it builds and runs
in-tree, but each "test" is a benchmark: it measures, prints a stable human-readable line,
and asserts a **loose** lower bound so it doubles as a perf-regression guard.

- `modules/gpu/test/test_bench.c` — the harness. `#if MEL_GPU_VULKAN`-guarded; on a
  non-vulkan build it compiles to a single skipping test.
- `modules/gpu/build.c` — one new target `gpu-bench`, mirroring the `gpu-vulkan` block
  (deps + the macOS AppKit link), plus an explicit `time` dependency for `<time/nano.h>`.

Timing uses `mel_nanos_since_unspecified_epoch()` — the monotonic high-resolution CPU clock
the `time` module exposes (the task's `mel_time_*` label; the real symbol is this). Each bench
runs warm-up iterations, then a measured loop over many ops; throughput benches report ns/op
(→ us/op + k ops/s), bandwidth benches report bytes/ns (→ GB/s), submit latency reports the
median over 2000 samples (plus min/mean).

### Benches

- **Resource-create throughput** — buffers, buffer create+destroy pair, textures, texture
  views, samplers, graphics pipelines. ops/s.
- **Upload bandwidth** — `buffer_write` (64 KiB / 1 MiB / 16 MiB) and `texture_write`
  (128² / 512² / 1024² RGBA8) → GB/s. This is the **synchronous-staging** cost: the engine
  stages to the device through an internal copy on the CPU thread, so this measures the whole
  host-side write path, not raw PCIe/UMA bandwidth.
- **Submit latency** — empty submission, `queue_submit` → `future_wait`, median us/submit.
  On the MoltenVK floor the submit resolves synchronously (the future is already resolved on
  return, per the `vk_queue` reference test), so the measured number is the full
  submit-to-retire wall time.
- **Allocator behavior** — churn 4000 odd-sized device buffers, sample
  `mel_gpu_memory_budget`; report peak live-bytes, the suballocator overhead (live ÷
  requested), and the deferred-free residual before/after a drain.
- **Bindless registration** — register/unregister many heap texture-views on a
  descriptor-indexing device (the §6.7 auto-registration hot path). ops/s.
- **Summary** — a closing prose block restating clock, backend, what is measured, and what is
  not (GPU time).

### Headline numbers (Apple M3 Pro, MoltenVK 1.2.334, debug build)

- `buffer_create` ≈ 17.5 us/op (≈57 k ops/s) — fresh-allocation path, no reuse.
- `buffer_create+destroy` ≈ 0.37 us/op (≈2.7 M ops/s) — ~47× faster; freed device memory is
  reused so no new VkDeviceMemory is claimed. The gap is the real cost of *retaining* the
  resources vs. recycling them.
- `texture_create` ≈ 5.7 us/op; `texture_view_create` ≈ 0.13 us/op; `sampler_create`
  ≈ 1.8 us/op (distinct lod_min defeats dedup); `pipeline_create` ≈ 37 us/op (full graphics
  PSO compile through MoltenVK).
- `buffer_write`: 0.19 GB/s @64 KiB, 3.1 GB/s @1 MiB, 20 GB/s @16 MiB (fixed per-write
  overhead dominates small sizes; bandwidth-bound at 16 MiB).
- `texture_write`: 0.37 GB/s @64 KiB, ~5 GB/s @1 MiB, ~5–13 GB/s @4 MiB (noisier — the
  staging copy + layout transition per write).
- `submit_latency_empty`: median ≈16 us/submit (min ≈9–11 us).
- `allocator_churn`: 118 MiB requested → 192 MiB live, overhead **1.62×** (buddy suballocator
  rounding, as the memory.c comment warns — up to ~2× for a just-over-power-of-two request).
- `bindless_register` ≈ 0.17 us/op (≈5.8 M ops/s); `bindless_unregister` ≈ 0.07 us/op
  (≈14 M ops/s) — the heap slot map is effectively free.

Result: **12 passed, 0 failed, 0 skipped**. Output is validation-clean — no `VUID`, no leak,
no validation error across the run.

### Thresholds (loose, CI-portable — generous, not tuned to this Mac)

- `buffer_create` < 200 us/op (measured ~17.5; ~11× headroom)
- `buffer_create+destroy` < 400 us/op
- `texture_create` < 500 us/op; `texture_view_create` < 300 us/op
- `sampler_create` < 400 us/op
- `pipeline_create` < 20 ms/op (measured ~37 us; ~540× headroom — PSO compile varies wildly
  across drivers, so this is deliberately enormous)
- `submit_latency_empty` median < 50 ms (measured ~16 us; ~3000× headroom)
- `allocator_churn`: suballocator overhead < 4.0×; `budget_bytes` > 0; post-drain residual ≤
  the churn peak (an always-true invariant — see kludge below)
- `bindless_register` / `bindless_unregister` < 300 us/op

The bandwidth benches print but do not assert a floor: throughput is too host- and
size-dependent to bound portably, and a bad number shows in the printed line.

## What could NOT be measured, and why

**True GPU execution time.** There is no `mel_gpu_query_*` / timestamp-query-pool API in the
public surface (`caps.queries.timestamp_period_ns` is populated, but nothing consumes it yet).
Every number here is **CPU-side wall time** — submission, staging, and the synchronous retire.
GPU-side pass/dispatch duration needs timestamp query pools (write-timestamp into a pool,
resolve, scale by `timestamp_period_ns`). That is the natural follow-up feature slice
(U-queries); the harness already has the device-create + submit scaffold a query bench would
reuse, so wiring GPU-time benches becomes mechanical once the query API lands.

## Kludges (MEL-ENGINE-VIII — full confession)

1. **No comments in the harness.** The house test files are densely commented, but my standing
   directive (`/Users/gabbo/CLAUDE.md`: "Never write comments") forbids it, and Rule #1 makes
   any exception need explicit permission I did not have. So `test_bench.c` carries zero
   comments while its neighbours are richly annotated — a deliberate house-style divergence.
   Flagging it for a ruling: if comments are wanted here, grant the exception and I will
   annotate. This is the one place the two rule-sets actively collide.

2. **Allocator-churn residual is a weak invariant, by necessity.** I first asserted that a
   post-destroy drain returns the budget to baseline. It does not: on this host
   `has_memory_budget` is true, so `mel_gpu_memory_budget().usage_bytes` is the **driver**
   `VkPhysicalDeviceMemoryBudgetPropertiesEXT.heapUsage` high-water (memory.c:236), and
   MoltenVK/Metal defers VRAM release — the number stays at 192 MiB long after the engine's
   deferred-free queue has retired (which the stress suite separately proves leak-free at
   device-destroy). The bench now **reports** deferred-before-drain vs. residual-after-drain as
   a retention signal and asserts only `residual ≤ peak` (always true). Honest, but it means
   the churn bench cannot, on this backend, *machine-verify* GPU-memory reclamation — only
   surface the driver's lag. A backend whose `usage_bytes` falls back to the engine counter
   (`allocator->used`, memory.c:243) would make a tighter assertion possible.

3. **`stdio` `printf` to stdout for bench lines.** The bench output bypasses the `log` module
   and writes straight to stdout (with `fflush`). Rationale: bench lines must be visible
   regardless of log-sink configuration, and the runner itself prints `RUN`/`ok` to stdout, so
   they interleave cleanly. Not strictly a kludge, but it is a deliberate sidestep of the
   logging subsystem (the test runner does the same with its `fprintf`).

4. **Per-worktree `nob` bootstrap.** `nob` is gitignored; I compiled it once via bare `clang`
   (`clang -std=c23 -g -Imodules/build -o nob nob.c`) before the first build. No repo change,
   but worth noting for anyone re-running in a fresh worktree.

## Suggestions (feature direction / hygiene)

- **U-queries (timestamp query pools)** is the obvious next slice — it is the only thing
  standing between this harness and real GPU-time profiling, and the caps already advertise
  `timestamp_period_ns`. A `mel_gpu_query_pool_*` + `mel_gpu_cmd_write_timestamp` surface, then
  a `bench_gpu_pass` here, closes the loop.
- The 47× create vs. create+destroy gap and the 1.62× suballocator overhead are both real,
  benign, and now *visible* — exactly the kind of thing a budget-pressure or fragmentation
  regression would perturb. Consider running `gpu-bench` in CI on at least one runner so the
  loose thresholds catch a real cliff (e.g. a backend that loses memory reuse).
- A `--gpu=d3d12` peer of this harness on win-pilot would let the budget-residual assertion
  tighten (D3D12 residency reporting is less lazy than Metal's), turning kludge #2 into a true
  reclamation check on that backend.
