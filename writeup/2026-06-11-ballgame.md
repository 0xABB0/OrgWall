# 2026-06-11 — ballgame: first pure game, win32 boot entry

## Work done

- **apps/ballgame** — a pure game: one ball, WASD movement (drag steers it on touch
  platforms). Boot-hosted setup, GUI canvas with `on_paint`, 60 Hz `mel_vat_tick_open`
  loop, `Mel_Frame_Clock` dt, keyboard + pointer callbacks, `mel_gui_set_focus` on the
  canvas. Ball clamps to the canvas bounds.
- **modules/vat/src/win32/waiter_msg.c** — win32 `mel_vat_waiter_ui`: pumps the thread
  message queue (`PeekMessageW`/`DispatchMessageW`) and parks in
  `MsgWaitForMultipleObjectsEx` over a doorbell event plus armed waitable HANDLEs;
  `ring` is an atomic flag + `SetEvent`. `mel_vat_waiter_io` aliases it.
- **modules/boot/src/win32/entry.c** — sovereign win32 entry; defines both `main`
  (console) and `WinMain` (gui subsystem, `__argc`/`__argv`), same run as the macos
  entry. Plus `lifecycle_stub.c` (same shape as web's stub). Boot readme updated; the
  stale "android entry owed" line was already wrong and the owed list now reads linux
  only.
- **modules/gui/src/dom** — fixed a wasm link failure for any gui app that creates no
  checkbox/slider: `backend.c` referenced `mel_web__checkbox_get`/`mel_web__slider_value`
  defined in `controls.c`; if no control symbol pulled `controls.o` from the archive the
  EM_JS import stayed undefined. Moved those two EM_JS getters into `backend.c`.

Verified: macos build+package+3s-alive smoke (twice), wasm link, ios-sim package,
android apk package, win32 link + 3s-alive smoke on win-pilot. `./nob test vat-core`
passes (10/10) on macos.

## Kludges (MEL-ENGINE-VIII — full confession)

- **win-pilot third-party cache surgery.** Fresh win32 builds of gmp fail on win-pilot:
  nob's autotools step needs `sh` and `m4`, and the box has neither on PATH (`m4` not
  installed at all; installing it was out of scope for this session's permissions). I
  built in a second git worktree (`D:\repo\OrgWall-ballgame`) and made gmp/mpfr pass by:
  robocopying the built `build/win32-debug` trees from the main checkout, rewriting the
  two `.thirdparty-built` stamps to the worktree's absolute prefix paths, touching the
  build trees newer than the checkout, and appending `C:\PROGRA~1\Git\usr\bin` (8.3
  short path, because libtool breaks on the space in "Program Files") to PATH so `make
  install` could run. The artifacts are genuine same-machine/toolchain builds, but the
  stamps now assert a configure that never ran in that directory. Debt: win32
  third-party builds are not reproducible from scratch on win-pilot until `m4` exists
  there; the documented `dev.cmd nob build` line does not actually suffice for any
  target whose closure includes gmp (every gui app — gui → math → mpfr → gmp).
- **`make install` cross-pollution.** The copied mpfr/gmp Makefiles bake the main
  checkout's prefix, so `make install` during my worktree builds rewrote
  `D:\repo\OrgWall\third-party\{gmp,mpfr}\build\win32-debug\prefix` with identical
  content. Harmless but it touched another checkout's build outputs.
- **Leftover worktree on win-pilot.** `D:\repo\OrgWall-ballgame` (branch
  `worktree-ballgame`) is still there with its build tree, to keep win32 iteration
  cheap. Delete with `git worktree remove` from `D:\repo\OrgWall` when done.
- **win32 waiter scope.** Wakeable handles are assumed to be waitable HANDLEs; bare
  SOCKETs can't arm (noted in boot readme). Nothing arms wakeables on win32 today.
- **win32 smoke depth.** The exe ran headless over SSH for 3 s and exited cleanly on
  kill; nobody saw the window or pressed WASD on Windows. Same caveat for ios/android/
  wasm: compile+package verified, not played. macos was run windowed but input was not
  injected.
- **`mel_vat_waiter_io` aliases the ui waiter on win32.** Message pumping on a non-UI
  thread is a no-op, so it works, but a dedicated IOCP waiter is the honest io story.

## CLAUDE.md suggestions (recommendations only, not applied)

- Windows builds section: note that nob's third-party autotools step needs `sh` and
  `m4`; today's win-pilot has neither (`sh` exists only inside Git for Windows — append
  `C:\PROGRA~1\Git\usr\bin` to PATH, short path on purpose), and `m4` is missing
  entirely, so gmp cannot configure from scratch there.

## Suggestions

- Install `m4` on win-pilot (one `choco install m4`) and the whole cache surgery above
  becomes unnecessary; fresh win32 builds would just work.
- The thirdparty runner could skip `make`/`make install` entirely when the fingerprint
  is fresh — it already trusts the stamp for configure; trusting it for install would
  cut win32/wasm rebuild chatter and remove the sh-on-PATH requirement for cached
  builds.
- A win32 vsync source (`mel_vat_vsync_open` is macos-only) would let games tick on the
  display clock instead of a 16.67 ms timer.
- boot's win32 lifecycle stub could forward `WM_ACTIVATEAPP` once a window exists;
  needs a window-module hook, same as the cocoa path uses NSApplication notifications.
- ballgame is a decent template for "interactive canvas app"; if a second game appears,
  consider extracting the tick+invalidate+frame-clock trio into a tiny `game` helper or
  an exemplar snippet in the gui readme.
