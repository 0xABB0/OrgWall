# baresensor — inventory
> api gen: bare image sensor — I²C/SCCB register map (control) + MIPI CSI-2 / parallel DVP (data), under an RTOS / bare-metal MCU-SoC, NO OS camera HAL, on-chip ISP OPTIONAL (SoC-sensor vs raw-Bayer split)
> covers matrix columns: embedded+baresensor

> The framework IS the driver. There is no OS camera API, no consent model, no vendor camera HAL: the sensor is a self-described register map reached over a 2/3-wire control bus (SCCB for OmniVision, I²C/CCI for Sony/onsemi), and pixels arrive as a MIPI CSI-2 (or parallel DVP/BT.656) stream that a SoC receiver DMAs into host-owned buffers. Two sensor classes dominate and split nearly every area: **SoC sensors** (OV2640/OV5640) carry an on-chip ISP — AEC/AGC/AWB, scaler, hardware JPEG — and deliver processed RGB/YUV/JPEG; **raw-Bayer sensors** (IMX219/IMX477/IMX296, AR0234) deliver a CFA mosaic and the host (or a SoC ISP, if present) must do 3A and demosaic itself. Most of the OS-era surface (live effects, virtual-camera egress, OS-integration consent/lifecycle, computational photography, OS-driven auto-3A) is simply ABSENT — that absence is the inventory. What the OS HALs hid is here NATIVE: manual exposure/gain by register, raw Bayer, readout/binning/crop windows, test patterns, PLL/blanking framerate, embedded metadata lines, hardware frame-sync/trigger/strobe pins, and direct register R/W.
> Register-name conventions: where a kernel `drivers/media/i2c/<sensor>.c` driver names a register field (e.g. IMX296 `SHS1`, IMX219 `FRM_LENGTH`), the NAME is cited; numeric addresses are NOT asserted (model level only). V4L2 subdev `V4L2_CID_*` IDs are the closest DOCUMENTED register abstraction and are cited verbatim from the kernel uAPI. `[soc-isp]` = present only on SoC sensors with an on-chip ISP. `[raw]` = the raw-Bayer-sensor surface. `?` = research-scheduled / unverified.
> Primary sources throughout: OmniVision SCCB Functional Spec v2.2; sensor datasheets (OV2640, OV5640, Sony IMX219/IMX477/IMX296, onsemi AR0234); MIPI CSI-2 v3.0 spec (31-May-2019); Linux kernel `drivers/media/i2c/*` + V4L2 uAPI (docs.kernel.org); libcamera RPi IPA CamHelper; Zephyr `video` API headers; STM32 HAL (DCMI/DCMIPP); Espressif esp32-camera.

## devices & enumeration
> There is no enumeration service. A bare sensor is wired at a known I²C/SCCB address on a known bus; the framework "discovers" it by probing its chip-ID register (the sensor's identity), not by asking an OS. Device identity lives in registers; topology is board-fixed (devicetree on Zephyr, a pin map in code on ESP32/STM32).
- `sensor chip-ID register` — read a known register pair to confirm sensor model+revision (the probe identity); drivers gate on it (`ov5640_check_chip_id`, `imx219` `CHIP_ID`) — source: OV5640/IMX219 datasheet (chip-ID); `drivers/media/i2c/ov5640.c`, `imx219.c`
- `I²C/SCCB slave address` — the sensor's fixed bus address (board-strapped); the only "enumeration" key — source: OmniVision SCCB Functional Spec v2.2 §3.5 (slave-only addressing); IMX219 datasheet (CCI address)
- `camera_config_t.{pin_*, sccb_i2c_port, xclk_freq_hz}` — ESP32: the board pin map + control-bus port + master-clock freq stand in for device identity; there is no list call — source: esp32-camera `driver/include/esp_camera.h`
- `DT_CHOSEN(zephyr_camera)` / `DEVICE_DT_GET` — Zephyr: the sensor+receiver are bound statically in devicetree; the app fetches the chosen camera node — source: Zephyr `samples/drivers/video/capture/src/main.c`
- `video-interfaces.yaml` endpoints (`data-lanes`, `bus-type` 4=MIPI-CSI-2-D-PHY / 5=Parallel, `remote-endpoint-label`) — Zephyr devicetree wiring of sensor↔CSI-2-RX (Zephyr uses a string `remote-endpoint-label`, not Linux's phandle) — source: Zephyr `dts/bindings/video/video-interfaces.yaml`
- `sensor_t.{id (sensor_id_t), slv_addr, pixformat, status}` — esp32-camera per-sensor identity+state struct returned by `esp_camera_sensor_get()` — source: esp32-camera `driver/include/sensor.h`
- `V4L2_CID_CAMERA_ORIENTATION` (READ-ONLY: FRONT/BACK/EXTERNAL) + `V4L2_CID_CAMERA_SENSOR_ROTATION` (mount rotation in degrees) — the documented mount-orientation surface the sensor/board reports — source: V4L2 uAPI Camera Control Class (`ext-ctrls-camera.html`)
- multi-sensor enumeration / hot-plug / vendor-API identity — ABSENT: no OS, no UVC descriptor, no GenICam XML manifest. Identity is the chip-ID register + the board's static wiring — source: (absence by design; cf. genicam `DeviceModelName`, UVC USB descriptors)

## topology & streams
> The data path is a fixed wire: sensor → (CSI-2 D-PHY lanes OR parallel DVP bus) → SoC receiver → DMA → memory. "Streams" means CSI-2 Virtual Channels and Data Types multiplexed on one physical link; "topology" is board wiring + which receiver port the lanes land on. No session graph, no app-defined connections — the framework configures the receiver to match the sensor.
- MIPI CSI-2 D-PHY link — 1 clock lane + 1–4 data lanes (unidirectional differential); the dominant raw-sensor data path — source: MIPI CSI-2 v3.0 spec §3, §6
- MIPI CSI-2 C-PHY trios — 1–N 3-wire lanes with embedded per-trio clock (alternative PHY) — source: MIPI CSI-2 v3.0 spec §6
- `Virtual Channel (VC)` — 2-bit legacy field = 4 logical streams interleaved on one link (image vs embedded data vs HDR sub-exposures) — source: MIPI CSI-2 v3.0 spec §9.2/§9.3
- `Virtual Channel Extension (VCX)` — v2.0+ widens the channel id: **16 VCs on D-PHY**, **32 on C-PHY** (the popular "32" is C-PHY-only); legacy RX treats VCX as 0 → 4 VCs — source: MIPI CSI-2 v3.0 spec §9.3
- `Data Type (DT)` — 6-bit packet field selecting the logical stream's payload kind (RAW8/10/12/14/16/20/24, YUV422, RGB565/888, Embedded-8bit, User-Defined) — source: MIPI CSI-2 v3.0 spec §9.2/§9.4, Tables 39/40/46/50
- CSI-2 receiver config surface — the framework configures the SoC RX for: #data-lanes (1/2/3/4), link rate (Mbps/lane), pixel-format/DT, frame W×H; D-PHY settle timing derived from sensor pixel-rate — source: Linux MIPI CSI-2 driver-api doc (kernel.org)
- SoC CSI-2 RX blocks (receiver-only, DMA to memory, NO demosaic) — RPi Unicam (Pi4, BCM283x/2711); RPi RP1 CFE (Pi5, 4 DMA engines→4 streams); NXP i.MX6/i.MX7 DW-CSI-2+gasket; TI CAL (AM5) / CSI2RX (AM6, Cadence); Rockchip rkcif/VICAP — source: kernel docs bcm2835-unicam / raspberrypi-rp1-cfe / imx7 / ti-cal / rkcif
- SoC CSI-2 RX blocks WITH post-receiver ISP `[soc-isp]` — Rockchip RkISP (rkisp1), Intel IPU3 (CIO2+ImgU), RPi PiSP/VC4-ISP, ESP32-P4 ISP, STM32N6 DCMIPP ISP pipe — these demosaic+3A after the RX — source: kernel docs rkisp1 / ipu3; ESP32-P4 TRM; STM32N6 HAL
- `video_stream_start/stop(dev, VIDEO_BUF_TYPE_OUTPUT)` — Zephyr: begin/end the configured pipe (no graph build, one sensor→one pipe) — source: Zephyr `include/zephyr/drivers/video.h`
- `cap.stream.multivs`-equivalent (one device, multiple kinds) — IS reachable as CSI-2 VC/DT multiplexing (e.g. image VC0 + embedded-data on the same link), but there is no app-facing "pin"/"port" object; it is receiver demux config — source: MIPI CSI-2 v3.0 §9.3 (VC); (no OS pin abstraction)
- multicam concurrency / cost-budget / logical-fused devices / switchover — ABSENT as an API. Multi-sensor IS a board reality (genlock pins, §timing), but there is no concurrent-session manager, no `hardwareCost`, no logical-multi-camera fusion — source: (absence; cf. avf `AVCaptureMultiCamSession`)

## fine-grained control
> THE native surface. Every "fine-grained control" the OS HALs gate behind 3A is here a direct register write over I²C/SCCB. The split: raw sensors `[raw]` expose only manual exposure/gain (no on-chip 3A — the host closes the loop); SoC sensors `[soc-isp]` add on-chip AEC/AGC/AWB and a full ISP tone surface. The V4L2 `V4L2_CID_*` IDs below are the documented register abstraction each driver maps to concrete registers.
- `V4L2_CID_EXPOSURE` — manual exposure/integration time (drivers express it in lines); on IMX296 written as `VMAX − value` to `SHS1` (name per `imx296.c`) — source: V4L2 uAPI Control Reference; `drivers/media/i2c/imx296.c`
- `V4L2_CID_ANALOGUE_GAIN` — gain applied in the analogue domain **before A/D conversion**, all colour components — source: V4L2 uAPI Image Source Control Class (`ext-ctrls-image-source.html`)
- `V4L2_CID_GAIN` / `V4L2_CID_DIGITAL_GAIN` — post-ADC digital gain; raw drivers split a requested total into analogue-first then digital-overflow (IMX219 `ANA_GAIN`/`DGTL_GAIN`, names per driver) — source: V4L2 uAPI Control Reference; `imx219.c`
- on-chip AEC/AGC `[soc-isp]` — OV5640/OV2640 compute exposure+gain ON the sensor (OV5640: 16-zone metering size/position/weight); driver exposes auto/manual clusters, auto-mode values are volatile read-back — source: OV5640 datasheet (AEC/AGC); OV2640 datasheet; `ov5640.c`
- on-chip AEC/AGC `[raw]` — ABSENT on IMX219/IMX477/IMX296/AR0234 (no on-chip 3A): the host must read frames and write gain/exposure registers back (software-3A loop) — source: IMX219 datasheet ("raw sensor without in-built ISP"); `imx219.c`/`imx477.c`/`imx296.c` (manual only)
- on-chip white balance / AWB `[soc-isp]` — OV5640/OV2640 on-chip AWB; raw sensors have no AWB (host applies WB gains during/after demosaic) — source: OV5640/OV2640 datasheet
- `V4L2_CID_TEST_PATTERN` (+ `_TEST_PATTERN_{RED,GREENR,BLUE,GREENB}`) — sensor test-pattern generator: IMX219 {ColorBars, SolidColor, GreyColorBars, PN9}; IMX296 10-entry {MultiplePixels, Sequence1/2, Gradient, Row, Column, Cross, Stripe, Checks}; OV5640 color-bar — source: V4L2 uAPI; `imx219.c`, `imx296.c`, `ov5640.c`
- black-level calibration (ABLC) `[soc-isp]` — automatic black-level on OV5640/OV2640; raw sensors leave black-level to host/SoC-ISP (some out-of-tree IMX296 forks add a `black_level` control — not mainline `?`) — source: OV5640/OV2640 datasheet; (mainline raw drivers: absent)
- ISP tone surface `[soc-isp]` — esp32-camera `sensor_t` setters: `set_contrast`, `set_brightness`, `set_saturation`, `set_sharpness`, `set_denoise`, `set_gainceiling`, `set_special_effect`, `set_wb_mode`, `set_ae_level`, `set_dcw`, `set_bpc` (bad-pixel), `set_wpc` (white-pixel), `set_raw_gma` (gamma), `set_lenc` (lens-correction), `set_aec2`, `set_awb_gain`, `set_agc_gain`, `set_aec_value`, `set_gain_ctrl`, `set_exposure_ctrl` — source: esp32-camera `driver/include/sensor.h`
- ISP tone surface `[raw]` — ABSENT: a raw sensor has no contrast/saturation/sharpness/gamma/CCM register; the host ISP (if any) or app pipeline owns tone — source: (absence; raw-Bayer model)
- on-chip autofocus `[soc-isp]` — OV5640 + esp32-camera `sensor_t` AF family (`af_init`, `af_trigger`, `af_get_status`, `af_set_manual_position`) on AF-capable modules — source: OV5640 datasheet (AF firmware); esp32-camera `sensor.h`
- direct register R/W — the bus is open: any documented register is writable. ESP32 `s->set_reg(s,reg,mask,value)` / `s->get_reg(s,reg,mask)` (masked SCCB passthrough); V4L2 `VIDIOC_DBG_S_REGISTER`/`_G_REGISTER` (debug ioctl, `V4L2_CHIP_MATCH_SUBDEV`, needs CONFIG_VIDEO_ADV_DEBUG+root) — source: esp32-camera `sensor.h`; V4L2 uAPI `vidioc-dbg-g-register.rst`

## mechanical controls
> Bare image sensors are fixed silicon: no pan, no tilt, no motorized zoom, no iris motor, no privacy shutter. Any optical motion is an external lens-actuator IC (e.g. a VCM autofocus coil driven over its OWN I²C bus), not part of the sensor register map.
- PTZ (pan/tilt/zoom) — ABSENT: a bare sensor has no motors. Pan/tilt is a mechanical mount; the framework has nothing to drive — source: (absence by design; cf. UVC `CT_PANTILT_*`)
- motorized optical zoom / iris / ND / filter-wheel / mechanical-shutter — ABSENT on the sensor; these are GenICam `OpticControl`-class motorized-lens territory, not silicon registers — source: (absence; cf. genicam `OpticControl`)
- VCM autofocus actuator (off-sensor) — AF-capable MODULES bolt a voice-coil-motor lens IC reachable on a separate I²C address; the sensor itself only carries the AF firmware/control handshake on SoC sensors (OV5640) — source: OV5640 datasheet (AF control); (VCM = separate IC, board-level)
- privacy shutter — ABSENT: no `CT_PRIVACY` equivalent; "privacy" on a bare sensor is cutting XCLK/power or asserting the PWDN pin — source: (absence; PWDN pin is power-down, not a privacy-policy control)

## capture modes
> Capture is the readout configuration + the trigger. NATIVE here: manual readout modes (binning/skip/crop windows), the snapshot-vs-continuous DMA choice, software single-shot, and the sensor's own hardware external-trigger/strobe pins — exactly the surface OS HALs collapse into a (size, fps) list. Computational photography (Night/HDR-fusion/Portrait), ZSL, bracketing-as-an-OS-feature: ABSENT (no ISP pipeline to run them — unless the app builds them).
- `snapshot vs continuous` capture mode — STM32 `DCMI_MODE_SNAPSHOT`/`DCMI_MODE_CONTINUOUS` (+ DCMIPP equiv); ESP32 `fb_count=1` (single-frame, wait-VSYNC-stop) vs `fb_count≥2` (continuous queue) — source: STM32 HAL `stm32*_hal_dcmi.h`; esp32-camera README
- `cap.capture.still` (software single-shot) — fire one frame: Zephyr enqueue+`video_stream_start`+dequeue; ESP32 `esp_camera_fb_get()`; no OS photo API — source: Zephyr `video.h`; esp32-camera `esp_camera.h`
- readout binning `[raw]` — IMX219 2×2 analog binning; IMX296 binning (mutually exclusive with crop, hardware limit); IMX477 binning via mode tables; OV2640 "VarioPixel" subsample; OV5640 scaler — source: `imx219.c`, `imx296.c`, `imx477.c`; OV2640/OV5640 datasheet
- readout skipping/decimation — subsampling readout modes selected by per-mode register tables — source: `imx477.c` mode tables; OV5640 datasheet
- readout crop / windowing (single ROI) — OV5640 cropping/windowing/panning; OV2640 zoom/pan/window; IMX219/IMX477 crop via mode tables; IMX296 crop (not with binning) — source: OV5640/OV2640 datasheet; `imx219.c`/`imx296.c`
- multi-ROI readout (≥2 regions) — ABSENT on these sensors as a register surface (`?` unverified per-sensor); CSI-2 v3.0 SROI (§9.14) is the protocol-level region mechanism, not exposed by the cited drivers — source: (absence in cited drivers); MIPI CSI-2 v3.0 §9.14 (SROI)
- global vs rolling shutter — FIXED per sensor, NOT a runtime select: global-shutter IMX296, AR0234, OV9281, OV2311; rolling-shutter OV5640, OV2640, IMX219, IMX477 — source: IMX296/AR0234 datasheet (GS); OV5640/IMX219/IMX477 datasheet (rolling)
- HDR / DOL / staggered readout `[raw]` — IMX477 sensor IS DOL-HDR capable but the OPEN driver does NOT implement it (register sets NDA-gated); libcamera `HdrMode`{Off,MultiExposure,SingleExposure}+`HdrChannel`{None,Short,Medium,Long} are framework hooks, unwired for bare IMX477. V4L2 `V4L2_CID_HDR_SENSOR_MODE` (menu) / `V4L2_CID_WIDE_DYNAMIC_RANGE` (bool) are the standard control IDs — source: `imx477.c` + RPi forum (NDA); libcamera controls; V4L2 uAPI Camera Control Class
- hardware-line external trigger — IMX296 XTRIG (low pulse starts integration; exposure = pulse-width + 14.26µs; pulse freq = fps; master-mode only); AR0234 TRIG (pulsed: 1 frame/pulse, min 125ns/3·EXTCLK; or automatic held-high); enabled via module-param/devicetree, NOT a runtime V4L2 control — source: IMX296 datasheet + RPi `external_trigger.adoc`; Kurokesu AR0234 driver
- OmniVision frame-sync input — OV9281/OV2311 `FSIN` pin (frame-sync input, synchronizes frame start across sensors); OV5640 `FREX` (frame-exposure/global-reset trigger) — source: OmniVision OV9281/OV2311 product briefs; OV5640 datasheet
- on-camera JPEG encode `[soc-isp]` — OV2640/OV5640/OV3660/NT99141 hardware-JPEG output (receive the camera's own bitstream); ESP32 `PIXFORMAT_JPEG`+`jpeg_quality` — source: OV2640/OV5640 datasheet; esp32-camera README (`support_jpeg`)
- ZSL / bracketing / burst / comp-photo (Night/HDR-fusion/Portrait/Bokeh) / deferred — ABSENT: no OS pipeline, no buffered ZSL ring, no extension session. An app may build a software bracket by re-writing exposure between frames, but there is no native bracket/sequencer object on these sensors — source: (absence; cf. avf/camera2 comp-photo; GenICam `SequencerControl` is industrial-only)

## depth / 3D / calibration
> A single bare 2D sensor produces no depth and ships no calibration data. Depth is a SYSTEM the framework would build: a second synchronized sensor (stereo, genlocked via XVS/XHS — §timing) plus host stereo-matching, or an external ToF/structured-light module on its own bus. Intrinsics/extrinsics are not in the sensor; they are a host-side calibration the app stores.
- depth map / disparity / point-cloud — ABSENT from a single bare sensor: no depth stream, no on-sensor stereo engine — source: (absence; cf. avf `AVDepthData`, genicam `Scan3dControl`)
- stereo rig (the reachable path) — two identical sensors genlocked by hardware sync pins (XVS/XHS master→slave, §timing) deliver frame-aligned L/R; depth is then HOST stereo-matching — the sensors give synchronized raw frames, not depth — source: Sony IMX415 datasheet (XVS/XHS master/slave); RPi camera docs (GS-Cam XHS tie for stereo)
- sensor physical geometry / pixel pitch — pixel-array size + unit-cell size are datasheet constants the framework must carry (no runtime accessor on a bare sensor beyond the datasheet) — source: IMX219/IMX477 datasheet (pixel array, unit cell)
- intrinsics / distortion / extrinsics / calibration delivery — ABSENT as device output: no `LENS_INTRINSIC_CALIBRATION`, no per-frame intrinsics chunk. Calibration is a host procedure; the sensor emits none — source: (absence; cf. camera2 `LENS_INTRINSIC_CALIBRATION`, genicam `Scan3dFocalLength`)
- IR / NIR / mono stream — NATIVE where the sensor is mono: IMX296LLR (mono), OV9281 (mono GS NIR), AR0234 mono variant deliver single-channel (no CFA, no demosaic). NIR illumination is a board LED the app strobes (§timing) — source: IMX296 datasheet (LLR mono); OmniVision OV9281 brief
- segmentation mattes (portrait/semantic) — ABSENT: no OS ML pipeline; any segmentation is app/CV-ML downstream — source: (absence; cf. avf `AVSemanticSegmentationMatte`)

## live effects
> ABSENT in full. There is no OS effects engine, no Center-Stage/auto-framing, no background blur/replacement, no studio light, no eye-contact, no reactions. The only on-silicon "effects" are the SoC-sensor ISP's fixed color presets (sepia/negative/mono) — a tone preset, not a live AI effect — and even those exist only on SoC sensors.
- auto-framing / Center-Stage — ABSENT: no digital-window auto-follow; cropping is a static readout window the app sets — source: (absence; cf. avf `centerStageEnabled`, mf `EXTENDED_DIGITALWINDOW`)
- background blur / replace / studio-light / eye-contact / reactions — ABSENT: no OS/firmware effect engine on a bare sensor — source: (absence; cf. mf WindowsStudioEffects, avf effects)
- color-effect preset `[soc-isp]` — the ONE near-effect: OV5640/OV2640 ISP fixed presets (mono/sepia/negative) via esp32-camera `set_special_effect` — a tone LUT, not segmentation — source: esp32-camera `sensor.h` (`set_special_effect`); OV5640/OV2640 datasheet
- subject-ROI tracking — ABSENT: no auto-tracking; an ROI is a static metering/crop window — source: (absence; cf. mf `ROI_ISPCONTROL`)

## frame memory
> The framework OWNS the buffers. The SoC receiver/DMA writes pixels into host RAM (DRAM or PSRAM); the app gets/returns buffers in a get-return ownership loop (Zephyr enqueue/dequeue, ESP32 fb_get/fb_return, NXP submit-empty/get-full). Pixel formats are whatever the sensor+DT emit: raw Bayer 8/10/12/14/16 (raw sensors), or RGB/YUV/JPEG (SoC sensors). DMA double-buffering (ping-pong) is the native cadence.
- buffer get/return ownership loop — Zephyr `video_enqueue`/`video_dequeue` (`struct video_buffer`, K_FOREVER); ESP32 `esp_camera_fb_get`/`esp_camera_fb_return` (`camera_fb_t`); NXP `CSI_TransferSubmitEmptyBuffer`/`CSI_TransferGetFullBuffer` — source: Zephyr `video.h`; esp32-camera `esp_camera.h`; NXP `fsl_csi` API
- buffer alloc — Zephyr `video_buffer_alloc`/`video_buffer_aligned_alloc`/`video_buffer_release`; ESP32 `fb_location` {`CAMERA_FB_IN_PSRAM`,`CAMERA_FB_IN_DRAM`} + `fb_count` — source: Zephyr `video.h`; esp32-camera `esp_camera.h`
- DMA double-buffer / ping-pong — STM32 `HAL_DCMI_Start_DMA`→`HAL_DMAEx_MultiBufferStart_IT` (M0AR+M1AR, re-armed in transfer-complete IRQ); DCMIPP `HAL_DCMIPP_PIPE_DoubleBufferStart`; receiver ping-pong + frame-done IRQ is the generic model — source: STM32 `stm32f4xx_hal_dcmi.c`+`_dma_ex.h`; kernel videobuf2
- back-pressure / drop policy — ESP32 `grab_mode` {`CAMERA_GRAB_WHEN_EMPTY`, `CAMERA_GRAB_LATEST`}; an exhausted pool stalls the producer (must return buffers) — source: esp32-camera `esp_camera.h`
- delivery format `[raw]` — raw Bayer over CSI-2: RAW8 (DT 0x2A), RAW10 (0x2B), RAW12 (0x2C), RAW14 (0x2D), RAW16 (0x2E); IMX219 sends RAW10 over 2/4 D-PHY lanes — source: MIPI CSI-2 v3.0 Table 40; IMX219 datasheet
- delivery format `[soc-isp]` — processed: YUV422/420, RGB565/555/444/888, GRAYSCALE, JPEG (esp32-camera `pixformat_t`: `PIXFORMAT_RGB565/YUV422/YUV420/GRAYSCALE/JPEG/RGB888/RAW`) — source: esp32-camera `driver/include/sensor.h`
- Zephyr pixel formats — `VIDEO_PIX_FMT_SBGGR8/SGBRG8/SGRBG8/SRGGB8` (Bayer), `_RGB565`, `_RGB24`, `_YUYV`, `_JPEG`, `_XRGB32`; `VIDEO_FOURCC(a,b,c,d)` packing — source: Zephyr `include/zephyr/drivers/video.h`
- format negotiation — Zephyr `video_get_caps`/`video_set_format`/`video_get_format` (`struct video_format`{pixelformat,width,height,pitch,size}); ESP32 `framesize_t` ladder (96X96…QSXGA/5MP) + `pixformat` — source: Zephyr `video.h`; esp32-camera `sensor.h`
- plane layout / stride — Zephyr `video_format.pitch`/`size`; STM32 line/byte select; raw is single-plane packed/CSI2-packed — source: Zephyr `video.h`
- demosaic of raw Bayer — NOT done by a bare-MCU receiver (STM32 classic DCMI, classic ESP32 = capture+DMA only): the app/framework demosaics in software/GPU, OR a SoC ISP does it (RkISP/IPU3/PiSP/ESP32-P4/STM32N6-DCMIPP `[soc-isp]`) — source: kernel docs (Unicam/CAL no-ISP); STM32N6 HAL `HAL_DCMIPP_PIPE_SetISPRawBayer2RGBConfig`

## timing
> The framework controls the clock tree end to end. The MCU GENERATES the sensor master clock (XCLK via PWM/LEDC or a dedicated clock-out); the sensor's on-chip PLL derives the pixel clock; framerate is set by writing VBLANK/HBLANK (blanking) and PLL registers. Multi-sensor genlock is real silicon: Sony XVS/XHS master→slave sync pins, XMASTER role-strap, IMX296 XTRIG. Per-frame timestamps come from the DMA/VSYNC interrupt, not an OS clock.
- master clock generation (XCLK/MCLK/XVCLK) — the MCU drives the sensor input clock; ESP32 via LEDC PWM (`ledc_timer`/`ledc_channel`/`xclk_freq_hz`, e.g. 20MHz); OV5640 accepts 6–27MHz → on-chip PLL → SysClk/MipiClk — source: esp32-camera README; OV5640 datasheet (PLL input range)
- PLL / clock-tree config — sensor PLL multiplier/divider register tables set pixel clock; surfaced at V4L2 as `V4L2_CID_PIXEL_RATE` (read-only px/s) + `V4L2_CID_LINK_FREQ` (CSI-2 lane-freq int-menu); ESP32 `sensor_t.set_pll`/`set_xclk` — source: V4L2 uAPI Image Source Control Class; esp32-camera `sensor.h`; IMX219/AR0234 link-freq tables
- framerate via blanking — `V4L2_CID_VBLANK` ("idle period after every frame") + `V4L2_CID_HBLANK` ("idle period after every line"); fps = PIXEL_RATE / ((W+HBLANK)·(H+VBLANK)); IMX219 VBLANK→`FRM_LENGTH`/HBLANK→`LINE_LENGTH`, IMX477 VBLANK is the framerate knob (HBLANK read-only), IMX296 both writable — source: V4L2 uAPI Image Source Control Class; `imx219.c`/`imx477.c`/`imx296.c`
- frame-rate clamp (alt path) — Zephyr `video_set_frmival`/`video_enum_frmival` (`struct video_frmival`{numerator,denominator}); ESP32/OV2640/OV5640 programmable frame rate via register tables — source: Zephyr `video.h`; OV5640/OV2640 datasheet
- per-frame timestamp — derived from the DMA frame-done / VSYNC interrupt: Zephyr `video_buffer.timestamp`; ESP32 `camera_fb_t.timestamp` (`struct timeval`); STM32 `HAL_DCMI_FrameEventCallback`/`VsyncEventCallback`. NOT an OS capture clock — the framework owns the time base — source: Zephyr `video.h`; esp32-camera `esp_camera.h`; STM32 HAL
- frame-sync / VSYNC / line events — STM32 `HAL_DCMI_VsyncEventCallback`/`LineEventCallback`/`FrameEventCallback` (`DCMI_IT_VSYNC`/`_LINE`/`_FRAME`); Zephyr frame-done via `video_set_signal`+`k_poll_signal` (`VIDEO_BUF_DONE`/`_ABORTED`/`_ERROR`) — source: STM32 HAL `stm32*_hal_dcmi.h`; Zephyr `video.h`
- hardware genlock / frame-sync pins — Sony XVS (vertical-sync) + XHS (horizontal-sync) master-out/slave-in genlock (IMX296/IMX415/IMX477); XMASTER/MAS pad straps master-vs-slave at reset (not software); GS-Cam stereo ties XHS test points — source: Sony IMX415 datasheet (XHS/XVS master/slave); RPi camera docs
- external trigger pulse → exposure start — IMX296 XTRIG (low pulse), AR0234 TRIG (pulsed/auto), OV9281 FSIN — the hardware-line trigger surface (§capture); GPIO/timer pulse on a bare MCU drives it directly — source: IMX296 datasheet + RPi `external_trigger.adoc`; Kurokesu AR0234 driver
- strobe output (exposure-window sync) — IMX296 STROBE (TOUT1/2, delay via PULSE1_UP); AR0234 FLASH (high during exposure, lead/lag shiftable); OV9281/OV2311 STROBE; OV5640/OV2640 LED/flash strobe — fire an LED synced to the (global-shutter) exposure window — source: IMX296/AR0234 module docs; OmniVision briefs; OV2640 datasheet
- rolling-shutter skew — first-to-last-row readout delay is reconstructable from line-time × height + VBLANK (the sensor exposes blanking, not a packaged `SENSOR_ROLLING_SHUTTER_SKEW`) — source: (derived from `V4L2_CID_HBLANK`/`VBLANK` + readout); cf. camera2 `SENSOR_ROLLING_SHUTTER_SKEW`
- PTP / SMPTE timecode / SDI genlock — ABSENT: no network clock, no embedded timecode; multi-cam sync is the XVS/XHS pin path, not PTP — source: (absence; cf. genicam `PtpControl`, DeckLink timecode)

## metadata
> The sensor's native per-frame metadata is the CSI-2 EMBEDDED DATA line: Sony raw sensors prepend a line carrying their register state (exposure/gain/frame geometry) as CSI-2 Data Type 0x12. It is delivered on a SEPARATE metadata path. Detection metadata (faces/barcodes), statistics maps, and OS-emitted bags are ABSENT — no ISP/OS to compute them (unless a SoC ISP emits 3A stats).
- CSI-2 embedded data line (DT 0x12) — "extra lines containing additional information at the beginning/end of each frame"; the per-frame sensor register dump — source: MIPI CSI-2 v3.0 §11.1.2, Table 39
- IMX219 embedded line `[raw]` — driver embedded-metadata pad: `code=MEDIA_BUS_FMT_SENSOR_DATA`, `IMX219_NUM_EMBEDDED_LINES=1` (one line, top, width 16384B); BUT libcamera sets `ENABLE_EMBEDDED_DATA 0` ("randomly returns junk register values") — parsing disabled by default — source: `imx219.c`; libcamera `cam_helper_imx219.cpp`
- IMX477 embedded line `[raw]` — `IMX477_NUM_EMBEDDED_LINES=1`, parsed by libcamera `CamHelper::parseEmbeddedData()` (enabled); falls back to reading `V4L2_CID_EXPOSURE`/`_ANALOGUE_GAIN` from the sensor if empty — source: `imx477.c`; libcamera `cam_helper_imx477.cpp`
- embedded-data delivery path — V4L2 `V4L2_BUF_TYPE_META_CAPTURE` on a separate metadata node, line-based (`V4L2_FMT_FLAG_META_LINE_BASED`), mbus `MEDIA_BUS_FMT_SENSOR_DATA`; modern mainline uses generic `V4L2_META_FMT_GENERIC_*`/`GENERIC_CSI2_*` fourccs (`V4L2_META_FMT_SENSOR_DATA` unverified `?`); Zephyr `video_buffer.line_offset` — source: kernel `dev-meta.html`/`metafmt-generic.html`; Zephyr `video.h`
- applied-settings echo `[raw]` — for sensors without (reliable) embedded data, the "applied" exposure/gain is read back by re-reading the sensor's own registers (the framework wrote them, the sensor confirms) — source: libcamera CamHelper fallback (read `V4L2_CID_EXPOSURE`/`_ANALOGUE_GAIN`)
- ISP 3A statistics `[soc-isp]` — only where a SoC ISP exists: RkISP/IPU3 stats nodes (AE/AWB/AF histogram), STM32N6 `HAL_DCMIPP_PIPE_SetISPStatisticExtractionConfig`/`ISP_GatherStatistics`. A bare sensor emits no stats map — source: kernel rkisp1/ipu3 docs; STM32N6 HAL/ISP_Library
- face/barcode/salient detection, OIS samples, lens-shading/hot-pixel/sharpness maps — ABSENT: no OS detector, no ISP statistics on a bare sensor — source: (absence; cf. camera2 `STATISTICS_*`, avf `AVMetadataFaceObject`)
- per-frame metadata bag (keyed attachment) — ABSENT as an OS object; metadata is the embedded line + register read-back, not a `CaptureResult`/`SPA_PARAM_Meta` bag — source: (absence; cf. camera2 `CaptureResult`, libcamera `Request::metadata()`)

## egress (virtual camera publish)
> ABSENT entirely. There is no OS, hence no "register as a camera" path — no CMIO extension, no MFCreateVirtualCamera, no v4l2loopback, no PipeWire node. The bare-sensor framework is a pure SOURCE: it ingests from silicon. Publishing a frame anywhere is the app's transport (the framework hands it a buffer; where it goes — display, network, file — is downstream).
- virtual-camera publish / frame push-pull / consumer attach — ABSENT: no OS virtual-camera surface exists on an RTOS/bare-metal target — source: (absence by design; cf. avf CMIOExtension, mf `MFCreateVirtualCamera`, v4l2loopback)
- install/packaging ceiling — N/A: there is no OS extension/driver/COM/kernel-module to install; the framework IS the driver, linked into the firmware image — source: (absence)
- synthetic/test source — the test-pattern generator (§fine-grained `V4L2_CID_TEST_PATTERN`) is the closest "synthetic source": the SENSOR emits a synthetic frame, useful for bring-up without optics — source: `imx219.c`/`imx296.c`/`ov5640.c` test patterns (a sensor feature, not an egress publish)

## OS integration
> ABSENT by definition — there is no OS. No consent prompt, no permission manifest, no session lifecycle/interruption, no arbitration, no privacy indicator, no thermal manager, no shutter sound. What an OS provides, the framework + board provide directly: power/reset/clock sequencing over GPIO, a physical button wired to a GPIO interrupt for "capture," and any status LED the board carries driven by the app.
- consent / permission / manifest / sandbox / usage-string — ABSENT: no OS consent model; access is physical wiring — source: (absence by design; cf. avf `requestAccessForMediaType:`, camera2 permissions)
- session lifecycle / interruption / background-block / arbitration / eviction — ABSENT: the firmware owns the sensor exclusively; no other process contends, no OS interrupts the session — source: (absence; cf. avf `AVCaptureSession` interruptions, camera2 `onDisconnected`)
- power / reset / clock sequencing — the framework's job: drive PWDN (power-down) + RESET (reset) GPIOs + start XCLK in the datasheet-mandated order before I²C probe; ESP32 `pin_pwdn`/`pin_reset` — source: esp32-camera `esp_camera.h` (`pin_pwdn`/`pin_reset`); sensor power-up-sequence datasheet sections
- hardware shutter button → capture — the app wires a GPIO button to an interrupt and calls the single-shot capture (the "shutter button" is literally a GPIO, no OS event) — source: (board-level GPIO; cf. the embedded pipeline shape — GPIO→still)
- status LED / privacy indicator — ABSENT as a managed surface; any in-use LED is a GPIO the app toggles (no OS-enforced privacy indicator) — source: (absence; cf. camera2 `SensorPrivacyManager`, genicam `DeviceIndicatorMode`)
- thermal management — ABSENT as an OS service; the framework may read a sensor die-temperature register where one exists (e.g. some Sony/onsemi parts), but there is no `systemPressureState` — source: (absence; cf. avf `systemPressureState`, camera2 thermal API)
- shutter sound — ABSENT: no regional-mandate sound, no audio service — source: (absence; cf. camera2 `MediaActionSound`)

## obscure corners
- SCCB ≠ I²C exactly — OmniVision's bus is I²C-like but the 9th (ACK) bit is a "Don't-Care" (NA) bit, max ~100kHz, CMOS push-pull; read is a 2-phase (dummy-write-then-read) cycle (no strict repeated-START) — source: OmniVision SCCB Functional Spec v2.2 §2.2/§3.5
- IMX296 master/slave is HARDWARE-strapped — the XMASTER pin at reset (not software) decides whether XVS/XHS are outputs (master) or inputs (slave); trigger enabled via module-param `imx296.trigger_mode=1`, not a runtime control — source: Sony IMX415 datasheet (master/slave); RPi forum (RPi camera engineer)
- 1.8V trigger/sync logic — IMX296 XTR, AR0234 TRIG/FLASH are 1.8V inputs; 3.3V can destroy the sensor (a hard hardware contract) — source: RPi `external_trigger.adoc` ("XTR is a 1.8V input"); Kurokesu AR0234 driver
- IMX296 exposure quirk — exposure written as `VMAX − value` to `SHS1` (the register is the complement of the desired integration); readout period is trigger-prohibited (~1126 lines all-pixel, height+38 cropped) — source: `drivers/media/i2c/imx296.c`; IMX296 datasheet
- IMX219 flip changes Bayer order — HFLIP/VFLIP shift the CFA phase, so the driver multiplies its mbus-format list by 4 to cover all flip×Bayer combinations — source: `drivers/media/i2c/imx219.c`
- IMX477 long-exposure shift — exposures beyond ~127s use a `long_exp_shift` scaling factor applied through VBLANK (HBLANK is read-only, capping naive max exposure) — source: `imx477.c`; libcamera CamHelperImx477
- BT.656 vs BT.601 sync — DVP can carry timing two ways: BT.601 = separate HSYNC/VSYNC wires; BT.656 = embedded SAV/EAV sync codes in the 4:2:2 stream (STM32 `DCMI_SYNCHRO_EMBEDDED` with `DCMI_CodesInitTypeDef`{FrameStart/LineStart/LineEnd/FrameEnd}); crop is unavailable in embedded-sync mode — source: ITU-R BT.656/BT.601; STM32 HAL `DCMI_CodesInitTypeDef`; STM32 AN5020
- ESP32 repurposes I2S for parallel capture — original ESP32/S2 have no camera unit: I2S0 is run in LCD/camera slave-RX mode (~8MHz PCLK ESP32, ~32 ESP32-S2); ESP32-S3 has a dedicated LCD_CAM (8–16-bit, ≤40MHz) + GDMA — source: ESP32 TRM "I2S Controller > LCD Mode"; ESP32-S3 TRM "LCD_CAM"
- DCMIPP is H7RS/N6 only — STM32 classic DCMI (F4/F7/H743/H753) is capture+DMA only; the DCMIPP pixel-pipeline + on-chip ISP (demosaic/exposure/CCM/black-level/bad-pixel/gamma/stats) exists only on STM32H7RS (single-pipe, no ISP) and STM32N6 (3 pipes + full ISP) — source: STM32H7RS/N6 HAL headers (`stm32n6xx_hal_dcmipp.h`)
- `VIDIOC_DBG_S/G_REGISTER` is gated — direct register debug ioctl needs CONFIG_VIDEO_ADV_DEBUG + superuser + per-driver opt-in (`V4L2_CHIP_MATCH_SUBDEV` selects the sensor); intended for `v4l2-dbg`, not production — source: V4L2 uAPI `vidioc-dbg-g-register.rst`
- esp32-camera has no public register-pair struct — `sensor_reg_t` is NOT in the public `sensor.h` (`?`); the public direct-register surface is the `set_reg(reg,mask,value)`/`get_reg(reg,mask)` masked SCCB passthrough only — source: esp32-camera `driver/include/sensor.h`
- `?` unverified — OV2640 test-pattern/flip control naming; AR0234 mainline windowing/binning/flip/test-pattern register exposure; black-level as a mainline raw-sensor control; embedded-data lines on IMX296/AR0234/OmniVision parts; IMX219 `XVS`/`XHS` pin exposure; CSI-2 v3.0 "Multi-Pixel Compression" as a named feature (not in v3.0 body); RP1/i.MX8M CSI register maps (datasheets draft/NDA); verbatim one-liners for `V4L2_CID_PIXEL_RATE`/`LINK_FREQ`/`TEST_PATTERN`/`DIGITAL_GAIN` (IDs confirmed used, doc one-line text not captured)
